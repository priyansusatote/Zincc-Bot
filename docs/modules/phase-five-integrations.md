# Connections and routines

Open the signed-in workbench and expand **Connections and routines**. The local slice is private to the current member in the selected workspace. The panel also shows the existing P3 Tasks grant. Its exact-write approval and revoke controls live in **Agents and runs**.

## Try a briefing

1. Choose Gmail, enter an account label and select **Add sample account**. Repeat for Slack with channel ID `CDEMO`. Sample accounts have two synthetic items each. During first sync, expand **Grant and sync** to watch the number of committed items grow. Wait for **ready** before running a briefing that needs that account. Expand **Grant and sync** to see the resource, scope and last successful sync.
2. Choose **Source briefing · v2**, review its permissions and install. Select the accounts the routine may read, give it a name, and choose a daily time and IANA time zone.
3. Select **Run now**. The receipt includes up to three recent items per selected account, labeled by account. A source that is unavailable produces a partial result. A revoked grant withdraws previously stored briefing text that used that source. Confirmed removal of a cached item also withdraws earlier receipts that used the account. This conservative rule avoids keeping a stale copy when the item is deleted or leaves the granted resource.
4. Create a second briefing with **When a selected source changes**. On a ready sample account, **Simulate incoming item** lets you exercise the change path locally. A real Slack notification requests a fresh provider read before the routine runs.
5. Choose **Dashboard refresh · v1** to recalculate a saved P4 dashboard. The receipt identifies the revision, total, unit and source page. Open the original dashboard for row-level evidence. Pause a routine to suppress new triggers and cancel pending runs. Resume calculates the next future slot.

Daily schedules skip nonexistent spring-forward times and use the first occurrence of a repeated autumn time. An offline interval coalesces into one catch-up when the service returns. A routine runs one job at a time, with independent manual attempt IDs and source-change receipts. A worker crash before commit leaves the read-only job eligible for replay. No private content is sent to a model in these routines.

## Connect a Google test account

1. Select a project in Google Cloud and enable **Gmail API** and **Google Calendar API**. Under **Google Auth Platform → Branding**, set an app name, support email and developer contact. Under **Audience**, choose External/testing for a personal Gmail account and add yourself as a test user. Select the Gmail read-only and Calendar events read-only scopes under **Data Access**. [Google Workspace credentials guide](https://developers.google.com/workspace/guides/create-credentials)
2. Under **Clients**, create a **Web application**. Add the exact authorized redirect URI `http://127.0.0.1:8080/api/integrations/callback`. Open the workbench using the same host. Place the ID in `ZINCC_GOOGLE_CLIENT_ID` and secret in `ZINCC_GOOGLE_CLIENT_SECRET`. The local `openrouter-free` profile loads the ignored root `.env` during startup. Restart after editing it.
3. The service also requires `ZINCC_CONNECTION_KEY`, a stable private 64-character hex value generated from 32 random bytes. Keep it alongside deployment secrets and include it in secure backups. Changing it requires reauthorizing existing accounts unless their ciphertext is migrated. Multiple service instances must use the same key.
4. In **Connections and routines**, turn off **Use sample account**, give the account a label and select **Authorize account**. Review the provider consent screen and return to the workbench. Repeat separately for Calendar or another account. Each grant uses a distinct connection ID and a fresh OAuth flow. Local-only mode disables provider authorization and network sync.
5. **Revoke access** removes the usable token and cached items from Zincc. A new login creates a new grant. Use the provider's account settings to remove upstream consent. Google's testing-mode token lifetime and administrator restrictions may require reconnecting. [Gmail sync semantics](https://developers.google.com/workspace/gmail/api/guides/sync) · [Calendar incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync)

Gmail sync lists all pages of the **INBOX** label, then follows history IDs and reads message metadata. The stored fields are the provider message ID, subject and timestamp. Calendar syncs event titles and start times from the primary calendar, including deletion updates. A full sync means all pages of the granted resource. Attachments, message bodies, draft/send actions, recurring-instance expansion and cross-provider priority scoring are outside this delivery.

## Connect a Slack test workspace

Create a Slack app from scratch. Add the bot scope `channels:history` under **OAuth & Permissions**. Use a bot installation with token rotation disabled for this adapter. Configure `ZINCC_SLACK_CLIENT_ID`, `ZINCC_SLACK_CLIENT_SECRET` and `ZINCC_SLACK_CALLBACK`. Register that exact HTTPS callback ending in `/api/integrations/callback` in the Slack app. The browser must return with its original Zincc session cookie. For a shared deployment, configure the HTTPS workbench and OIDC origin consistently. The default loopback HTTP workbench needs an HTTPS configuration for Slack consent. A public deployment or tunnel is a separate operator action. [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/)

Authorize the account, invite the installed bot into the selected public test channel and copy the channel ID into Zincc. The connector reconciles a rolling 24-hour channel history. It uses a fixed window while paging, enforces rate-limit delays, and replaces a snapshot only after its final page. Thread replies, private channels and DMs require separate scope and qualification. For event hints, set `ZINCC_SLACK_SIGNING_SECRET`, register the HTTPS endpoint `/api/integrations/slack/events` in **Event Subscriptions** and select `message.channels`. Polling works without webhook delivery. Zincc checks the raw signature, timestamp, team and channel, deduplicates deliveries and ignores bot-originated message notifications. [History API](https://docs.slack.dev/reference/methods/conversations.history/) · [Signed notifications](https://docs.slack.dev/authentication/verifying-requests-from-slack/)

## Operations and verification

Apply Flyway V8 before starting with the `oidc,agents` profiles. Enable `knowledge` and configure the P4 pinned `ZINCC_KNOWLEDGE_IMAGE` for reports and the curated MCP briefing tool. The tool uses a fixed stdio command inside a short-lived local container with no network or account credentials. It supports MCP revision `2025-06-18`. Its approved schema is checked before the client sends private summaries. [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

Run `./mvnw verify` for the database and protocol suite. For the live browser journey, use a dedicated signed-in local test workspace with the P4 invoice fixture and an **Invoice totals** dashboard filtered to North. Set `ZINCC_TEST_USERNAME` and `ZINCC_TEST_PASSWORD` privately and run `node frontend/tools/qualify-integrations.mjs` from the project root. The optional `ZINCC_TEST_DASHBOARD` and `ZINCC_TEST_EXPECTED_TOTAL` override the default dashboard and total. The script leaves the named sample accounts, receipts and paused example routines available for inspection.

The poller discovers up to 32 due IDs and runs up to two jobs per instance. Each job rechecks membership under PostgreSQL row-level security. Provider fetches and tool reads hold bounded-work row locks. High-volume installations need provider-specific quotas, retention policy, secret-key rotation and multi-instance load qualification. The acceptance journey uses sample accounts. Real Google or Slack behavior requires testing with a consented account and a configured provider app.
