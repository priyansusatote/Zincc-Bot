## Recommended product changes

1. **Show what changes when I switch models.** OpenMausBot's picker tests distinguish switching the current conversation, changing a bot default, and stopping an active turn to switch AI. Its usage tests tie quota information to the reporting engine. Zincc already freezes the accepted run's model and grant. Show the effective account and model, offer **Change for next run** as the default, and surface remaining allowance only when the provider reports it, with its observation time. An immediate restart should show already-issued actions before a new run can repeat them. Acceptance example: changing the default during a calendar task leaves the running task's receipt intact and changes the next run's receipt. [Switch behavior](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/src/components/ModelPicker.ai-switch.test.ts) · [Usage behavior](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/src/components/ModelPicker.usage.test.ts)
2. **Give users one place to see which agents need them.** The upstream sidebar counts working, waiting and unread activity and counts an unread waiting bot once in its combined total. For Zincc, prioritize unresolved decisions across the signed-in member's agents. Each entry should say what is blocked, link to its run, and disappear when the decision resolves, including from another tab. A finished briefing can stay unread without looking like an outstanding approval. Derive this view from existing authorized run and approval records. [Sidebar aggregation](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/src/lib/sidebar-attention.ts)
3. **Explain exactly why a desktop task is waiting.** The upstream computer request flow distinguishes a closed app, paused access and missing OS permission. Its tests cover repeated asks, declining and stopping. For a Zincc Paint task, show the device, requested capability and next action. If the runner is offline, say to open it. If access was declined, suppress duplicate prompts. When it reconnects, recheck the original member, device and grant before resuming. A reconnection alone must never grant desktop control. [Request state](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/server/computer-asks.ts) · [Behavior cases](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/server/computer-asks.test.ts)

## What a subscription picker can promise

OpenCode's probe reads provider-qualified model IDs from the engine session. Antigravity reads options for the current Google account. Kimi's tests cover both a rejected selection and an apparently successful switch that kept the old model. A catalog entry is evidence of discovery. A verified Zincc route also needs a permitted provider interface, a matching model acknowledgement where an exact choice is offered, and a successful task receipt. Use Zincc's own client identity. Omit options that the provider does not offer that client. [OpenCode discovery](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/server/drivers/acp/opencode-probe.ts) · [Antigravity driver](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/server/drivers/antigravity-acp.ts) · [Kimi selection cases](https://github.com/milind-soni/OpenMausBot/blob/fcce0b6ded3a74ad366debcc37e1a67c626bff3b/server/drivers/acp/kimi-model-selection.test.ts)

The existing P9 engine workbench already has agent defaults, member-private conversation overrides, grant checks and per-run receipts. Its ordinary chat picker remains separate. The latest recorded Windows evidence is a completed Antigravity task with Gemini 3.8 Flash, an HTTP 429 on OpenCode Free, and a pending ChatGPT consent callback. The three recommendations above are product backlog candidates. They introduce no new dependency or provider qualification.
