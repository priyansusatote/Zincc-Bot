# Firecrawl and TurboQuant

## Firecrawl → web research and source refresh

Firecrawl separates discovering URLs, extracting one page and tracking a crawl. At revision `1510bc4` the map controller handles sitemap and cache choices, the scrape controller preserves the original requested URL and distinguishes cache misses, and the crawl-status controller reports counts and credits. These are useful distinctions when a user asks “What changed in these product docs?” A successful crawl can still have missed the one page that mattered. [Map](https://github.com/firecrawl/firecrawl/blob/1510bc4fff9c7014f6fa5be0f821ece168a69d13/apps/api/src/controllers/v2/map.ts) · [Scrape](https://github.com/firecrawl/firecrawl/blob/1510bc4fff9c7014f6fa5be0f821ece168a69d13/apps/api/src/controllers/v2/scrape.ts) · [Crawl status](https://github.com/firecrawl/firecrawl/blob/1510bc4fff9c7014f6fa5be0f821ece168a69d13/apps/api/src/controllers/v2/crawl-status.ts)

For P2.4, record requested URL, final source URL, observation time, fetched versus cached status and partial coverage alongside citations. Evaluate an optional Firecrawl HTTP adapter on permitted public sources with page, time and spend limits. A later user-created watch routine could report changed passages with before/after citations. Compare hosted and self-hosted behavior on the same fixtures before offering either. No crawler or upstream source was added. ## TurboQuant → local inference experiment

The supplied article explains how attention stores keys and values for earlier tokens and why long contexts increase GPU memory use. The research compresses vectors, including the inference engine’s KV cache. The paper reports near-baseline quality at particular bit widths on its evaluations. That result depends on the model, workload and implementation. It does not establish a Zincc end-to-end latency or memory improvement. [Article](https://aiengg.dev/blog/google-turboquant) · [Authors’ paper](https://arxiv.org/abs/2504.19874) · [Google Research](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/)

Add a comparison to L-INFER-01 when a supported serving engine and GPU are available. Hold model revision, hardware, prompts, concurrency and context lengths fixed. Compare baseline and compressed KV memory, maximum sustainable context, time to first token, decode throughput, retrieval accuracy and structured-answer validity. Record regressions as well as gains. Quantization belongs inside the serving engine. Zincc’s gateway can consume measured capability limits later. No compression code or performance claim is adopted in P2.1.
